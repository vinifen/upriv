# Store crypto (Argon2id + XChaCha20-Poly1305)

## Stance

At rest the vault body is **`store/`** (Argon2id → HKDF → XChaCha20-Poly1305 chunks, AES-SIV names). **Backups** are frozen copies of that body. Portable files: ordinary **`.zip` of `store/`** (Recommended; zip is an envelope, no zip password) or **`.7z`** (Plan B). AES-256 in 7-Zip is not “broken”; we use Argon2id + AEAD for **offline password guessing**, not because XChaCha beats AES.

Never claim “more secure than 7-Zip” or “the same security as VeraCrypt.” Round-trip encrypt/decrypt is not a security proof. Closed-disk residual attack = guess the password paying Argon2id. In-app 5/60s throttle is not anti-offline.

## Do

- Primitives only via a mature library (no hand-rolled ChaCha/Poly1305/Argon2). Those crates are pinned in `dev/vendor/` (`[patch]`). Refresh is the checklist in `dev/vendor/MANIFEST.txt`; do not `cargo generate-lockfile`. Do not edit `vendor/*/src` except in a reviewed upgrade.
- Unique random salt; persist KDF params in `vault.header`. Cost is chosen **at vault create** (default **256 MiB / 3 passes**; also **128 MiB / 3**, **64 MiB / 3**, **32 MiB / 3** less-secure opt-in, **1 GiB / 1**, **2 GiB / 1**). UI: security of each preset + RAM needed to unlock — **not** phone vs desktop. Open uses the header everywhere. **Never** auto-pick or lower params because of the current device.
- The header holds a keyring: a top block (`generation`, `kdf`, `key_ids`, `since`, `wrapped_keys_b64`), and a `change` block only while a password change is pending; at most 8 keys, ids that only grow, the newest the write key. Password unlocks the keyring once per open; each write = the write key's content key + new 192-bit CSPRNG nonce (not Argon2, not a RAM counter), and the chunk's version is derived from that nonce. A read picks each chunk's key by the id its index entry names. See SECURITY-CRYPTO “Password, keys, edits, nonces”.
- Every blob starts with a 4096-byte key copy, the header block it was written under byte for byte, so any blob plus the password opens that file; chunks start at 4096. Every flow that writes a blob keeps it through `StagedBlobs`, and after a header write that changes the top block the pass (`key_copies_due`) makes every key copy, `held/` included, the header's.
- A password change (`vault_change_password`) makes a new key and rewrites every file with it, batch by batch, on a closed vault; **Back up first** writes a Save when there is room and never blocks it. A stop puts a fresh key, never under the new password, as the write key; a crash leaves a pending change that the new password settles forward and the old password cancels only when nothing was converted (`password_change_interrupted` otherwise); an unfinished one offers Finish (`vault_password_change_finish`). After a finished change and its pass the vault holds one key and no earlier one. An unlock-RAM change (`vault_change_kdf`) keeps the keys, reseals the header and the name index, and runs the pass; it writes no backup. Same password or same preset is rejected first (the preset from the header, before any unlock). A wrong password, an earlier one (`password_outdated`), and `password_change_interrupted` each count once for the unlock throttle.
- One unlock rule for every caller: both header files, every block they hold, then the index under the pairs that block may use; a pending change is decided first; nothing is written before a header and an index open together, and only then is a twin repaired. A failed unlock samples the first 72 bytes of up to 4 blobs to tell `wrong_password` from `password_outdated` and `vault_header_unreadable`.
- AEAD AAD is compact `serde_json` of a **struct in field order** (not pretty `vault.header`, not RFC 8785). One store format (`format_version` 1). Wrap and index bind version, **content identity** (not registry folder id), algos, and their block's KDF params; the index opens only under the pair of the vault's header (its write key's index key and that block's AAD). Chunks bind version, content identity, file id, chunk index, chunk length, and the version derived from their nonce — not KDF salt/`m`/`t`/`p` and not `file_size`. Any other `format_version` is an unreadable store. Verify tags before any plaintext leaves `upriv-core`. An index that unseals is also checked as a tree (valid paths, one node per path, a folder above each node, one file per blob) and does not open when it breaks a rule.
- `password_hint` in `config.toml` is **public** (list without unlock). UI must say so. Empty hint is safer than a hint that is the password.
- `store/` = live ciphertext. A backup is one **Stored** zip, no zip password: `README.md` and `config.toml` beside `store/` in `<stamp>-<id>.zip` (pins: `saves/<stamp>-<id>.zip`; a named backup is `<stamp>-<id> <name>.zip` in `saves/`), in the vault's backup folder in use: the data folder (`.upriv/vaults/<id>/backups/`), or a row of this device's backup lists, where a failing folder hands the selection over to the next choice of its chain that works, with a toast. A row's folder holds only ciphertext zips, is never inside a `.upriv`, and never inside an `upriv-unlocked` folder, nor the other way round. Every zip has a reference to its folder in `persistence.json`; writes and rotation happen only in the folder in use, and automatic deletion touches only the zips in `backups_written`. `README.md` records the UTC time of that copy and the rounded size of the files in `store/` (not the exact length of the zip). That zip is the only backup form. Close streams that envelope straight into the zip; Close now writes none, and the next normal close does. Create-from-backup unpacks `store/` into a **new** vault, keeps the settings in that vault's own `config.toml`, and writes `DANGER-DO-NOT-EDIT-PERMANENT-DATA-LOSS.md` into the new `store/`. Export and backup write that same file before packing so the zip keeps it inside `store/`. The new vault does not keep `README.md`. Backup export copies one `.zip` into a chosen folder, or bundles several snapshot zips into one Stored zip; it never replaces a file already using the name. Export data folder zips the whole `.upriv` the same way (Stored, no zip password), with each vault's `backups/` unless Include backups is off, while every vault is closed or in recovery: ciphertext as it is, never decrypted, as `<name>.zip` holding `<name>/<folder>/.upriv/` (the data folder keeps its own name inside). Export of the live vault is the same envelope inside a package: one folder named like the file, holding one folder named after the vault's id (`{display_name}-upriv/{vault_id}/`). An import names the vault after the name its settings carry, or else that folder, so renaming the file never renames the vault an import makes. A backup zip is no export and keeps the envelope at its root. User chooses a `.zip` of `store/` (**Recommended**), a `.7z` (warn: weaker offline guessing), or a plain-text `.zip` (**Insecure**, not encrypted at all, behind the vault password). The file is **`{display_name}-upriv.zip`**, **`{display_name}-sevenzip.7z`**, or **`{display_name}-plain-text.zip`** (not registry id) in the folder the person chose, and never replaces a file already using that name: it takes the next free number (`{display_name}-upriv-2.zip`). Export requires **that** vault closed (other vaults may stay open). File zip/7z import and create-from-backup copy a frozen tree — they do not require the source vault closed. `.7z` never stores `.enc` blobs and does not carry the store-zip envelope. A `.7z` and a plain-text `.zip` hold the vault's files in the package's vault folder. Both may carry `.upriv-config/` in the package folder, beside the vault folder, so the vault folder holds only the vault's files: `config.toml` and `workspace.json` (each behind its own export toggle, on by default) with a `README.md`. A new vault moves what that folder carries to its place and never keeps the folder. The zip envelope has **no** zip password. **Do not** present the zip as a custom “Upriv file” type — it is a normal `.zip` whose payload is Upriv ciphertext. A store zip is recognized by `store/header/vault.header` at the zip root (a backup) or in an export's package, not by a file merely named `vault.header`, a `store/` in one folder, or a root `config.toml`. **Mobile:** same `store/` session via in-app file manager (no FUSE); never copy the vault to `filesDir` / OS temp to fake a mount.
- Recovery: dirty close or leftover `upriv_plain` folder. Both header files dead, gone, or older than the blobs (`vault_header_unreadable`), or both index files dead or gone under a header that opens (`vault_index_unreadable`) → the row is recovery, and the person may rebuild (`vault_rebuild`, refused while a header and an index open together; the vault opens once it lands): the header from the blobs' key copies, the tree from their recovery records and the backups. Create-from-backup is the way back only when no key copy opens. A file whose data is missing or fails its tag → that file is marked and kept (`VaultFileUnreadable`), the vault still opens, and no other operation stops for it: exports keep it with zeros, close compaction skips it, a lost blob never blocks a seal. Never delete it for the person, and never rewrite it, except a copy: every copy carries an unreadable chunk byte for byte with its version, so it stays unreadable (the copy after a failed flush keeps its key id; a password change gives it key id 0). A blob no file names is never deleted either, whatever its length: the unlock that opens a session (or comes before a password or unlock-RAM change) moves every such regular file to `vaults/<id>/held/`, records it in the sealed index, and names its file from its own recovery record or a backup when one still names it; only the person puts it back or deletes it. A blob the index lists as `released` is deleted by the first seal that flushes, only in a session whose unlock marked no file missing for the first time; otherwise it is set aside too.
- Recovery records: each blob carries sealed copies of its file's index entry after its chunks, under its own HKDF key (`upriv-record-key-v1`), AAD binding version, content identity, algorithm, `kind` `"record"`, file id, and `seq`. A blob gets one at the seal that first names it (an import writes it in its worker, before that worker's flush) and one at the close of each session that wrote to it since; never at every mid-session seal (a record lists every chunk). Written before the blob's flush, never rewritten, never read by an open, a read, a write, or an export: only set-aside naming and the rebuild read them, decrypt first, then check. A record is sealed with the write key's record key and read by trying keys, newest first. A record that cannot be written is logged and the seal goes on. After any header step and before the tree step, the rebuild writes a copy of `store/` in `saves/` of the data folder, which stays until the person deletes it, and goes on without it when it does not fit or fails; it names each blob from the newer of its own record and the newest backup that names it (higher save number; the backup on a tie), never moves, rewrites, or deletes a blob, and leaves a blob nothing places in `data/` for the next unlock to set aside. Chunk placement keeps off the newest record; the waste measure counts older records as waste and the newest not.
- Seal: first flush every blob written, each shard folder holding a new blob, then `data/` (`StagedBlobs`, one helper for every save). A blob whose flush failed, or that sits under a folder whose flush failed, is copied to a new blob, never flushed again; a failed folder flush of the index copy makes the whole seal unflushed. An error leaves the previous primary index, so undo the change and delete its new blobs. A primary in place whose folder flush failed keeps the change and every byte the previous index names until a later seal flushes. Every seal lists the blobs it drops in `released`, and when both index files open with different trees the higher `saves` wins (the primary on a tie), so a crash between a seal's two writes leaves nothing for `held/`. Any write of a header or index file of a closed vault records `content_hash` (both header files and the primary index) in the same step. Never retry a failed `fsync`.
- Greenfield. `dev/` is the first product, not a successor. One store format (`format_version` 1). One backup file: `<stamp>-<id>.zip` (pins: `saves/<stamp>-<id>.zip`). No reader, migrator, or second path for any other format or layout. New work is the current path only — do not keep a compatibility shim next to it.
- Delete vault is a job: `[deleting]` in `config.toml` first, each blob's key copy overwritten before it goes, `config.toml` last, so a crash leaves a `deleting` row with Continue; Delete now (`vault_delete_hurry`) removes what is left with no overwrite.
- Lock = close, the only lock action. Close now is that close with no backup and, on `upriv_plain`, no closing pass and no overwrite; it still seals the index and drops the keys. A close already running can be told the same (`vault_close_hurry`), and the seal still finishes. Persistence on disk is `closed` only.
- Surface anti-brute-force: in **`upriv-core` session RAM** — serialize `open`; **5** failures / **60 s** → **60 s** block. Resets when the process exits. **No** JSON attempt counter. Does not stop offline guessing.
- Plaintext vault bytes on ordinary disk **only** for `upriv_plain` while open (the files sent to its folder, or every file with `plain_files = "whole"`), and as the plain-text `.zip` a person chose to export.
- The storage value (mode and `plain_files`) is sealed in the index; `[storage]` in `config.toml` is its copy. An open writes plain text only when both say `upriv_plain`; when they differ it opens encrypted with no unlocked folder and resets both to the default (copy first, the sealed value once that landed), and never refuses. A missing or unknown value, in either, reads as the default (`encrypted_dir`, `chosen`). Only the Storage change (`vault_change_storage`: closed vault, the password, index then copy) moves it; a settings save never changes `[storage]`. Store-zip and backup copies keep the sealed value they carry, with the carried copy; the rebuild of the tree seals the default. Import/export/backup/password/recovery must not stage a decrypted tree (including “temp for 7zz”).

## Do not

- Weaken or auto-downgrade the KDF, or pick a preset from device type (phone/desktop).
- Use raw Argon2 output as every layer’s key (use HKDF domain separation).
- Pack `.enc` blobs into `.7z`; put a zip password on a store zip or a backup zip.
- Add a lock action other than close, or a storage mode besides `encrypted_dir` and `upriv_plain`.
- Let `config.toml` alone decide the mode, or let any change of the storage value skip the password (a reset and the rebuild, which only turn plain text off, are the exceptions).
- Claim in-app unlock backoff “prevents brute force,” or implement that backoff only in TypeScript.
- Implement crypto in TypeScript / Electron / Expo.
- Reorder AAD struct fields or “canonicalize” AAD JSON without a `format_version` bump.
- Put KDF salt/`m`/`t`/`p` or `file_size` back into chunk AAD.
- Keep an earlier key in the vault: a password change ends with one key, unreadable chunks and missing files get key id 0, and only backups hold earlier keys. Write with a key that was ever on disk under another password than the vault's.
- Write a blob outside `StagedBlobs`, or leave a key copy behind the header once its pass ends.
