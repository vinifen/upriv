# Pull requests

## Target branch

| PR targets | Typical source | Merge |
|------------|----------------|--------|
| **`develop`** | `feat/…`, `fix/…`, `docs/…` | **Squash** — one conventional commit on `develop` |
| **`main`** | `release/…`, `hotfix/…` | **Merge commit** — keep the release topology. Do not squash |

The squash commit subject should be the **PR title** (same `type(scope): summary` shape as [COMMITS.md](COMMITS.md)).

## Title

```text
type(scope): short imperative summary
```

Same types/scopes as commits. Entire title ≤ **120 characters** (same cap as the commit subject). No emoji, no special characters. No “WIP” on a PR you intend to merge.

Link the issue in the title only if it stays short; otherwise use `Fixes #N` in the body.

## Body

Use [`.github/pull_request_template.md`](../../.github/pull_request_template.md). Fill it; do not leave placeholders.

| Section | What to write |
|---------|----------------|
| **Summary** | Prefer **bullet points** (paragraphs OK if needed). What changed and **why**. English. Not a file dump |
| **Related issue** | `#N/A` unless an issue exists (`Fixes #N` / `Related to #N`) |
| **Checklist** | Two boxes only: no secrets in the diff; tests ran (`./run check` from `dev/`, or what you ran) |

Do **not** mention an AI, model, or editor in the PR title or body. Do not add a footer. These are forbidden, including when a tool appends them after `gh pr create`:

- `Made with Cursor`
- `Made with [Cursor](https://cursor.com)`
- `Co-authored-by:`
- `Made-with:`
- `Generated-by:`
- `Assisted-by:`
- any “Generated by …” or “Made with …” line

After creating or editing a PR, read the body back. If any of those lines is present, delete it with `gh pr edit` before treating the PR as done.

## When to open a PR

| Who | Rule |
|-----|------|
| External contributors | Always. Fork → branch → PR into `develop` |
| Maintainer | Prefer a PR into `develop` (CI + reviewable diff). Direct push to `develop` is OK for a **trivial one-commit** chore |
| Nobody | Direct push to `main` |

Even as a solo maintainer, a PR is the right default for anything larger than a typo: CI runs, the template forces the two-box checklist, and the squash keeps `develop` readable.

## Agent procedure

Only when the human asked to open a PR.

1. Confirm the branch tracks the intended base (`develop` unless hotfix/release).
2. Push with `-u` if needed. Do not force-push `main` or `develop`. Force-push a **personal** working branch only if the human asked and it is not shared.
3. `gh pr create` with title + body HEREDOC matching the template. Base: `develop` (or `main` for hotfix/release).
4. Read the saved body (`gh pr view --json body`). If it contains `Made with Cursor`, `Made with [Cursor](https://cursor.com)`, `Co-authored-by`, `Made-with`, `Generated-by`, or `Assisted-by`, run `gh pr edit` with the same body and those lines removed, then read it back again.
5. Return the PR URL only after the body has none of those lines.

Do not add reviewers, labels, or GitHub “co-author” metadata that credits a tool.

## Review

Until there are regular collaborators, the maintainer may self-merge after CI is green.

When someone else is contributing: at least one human approval; the author does not count as the only reviewer for security-sensitive diffs (`upriv-core` crypto, vault I/O, export/import).

## After merge

Delete the working branch. Do not leave `feat/…` branches stacked on GitHub without a PR.
